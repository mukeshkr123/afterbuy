## 1. Conventions

### 1.1 Versioning and auth

- Base path **`/v1`**. `GET /health` stays unversioned.
- `Authorization: Bearer <clerk-jwt>` on everything under `/v1` except
  `POST /v1/webhooks/clerk` (Svix-signed instead).
- The OpenAPI document **must declare a security scheme.** It currently declares
  none, which means the generated spec claims the API is public.

### 1.2 Error envelope

Extend the existing `{ error, requestId }` shape rather than replacing it:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Purchase date is invalid",
    "fields": { "purchaseDate": "must be ISO-8601 date" }
  },
  "requestId": "01JG…"
}
```

| code                | status |
| ------------------- | ------ |
| `unauthenticated`   | 401    |
| `forbidden`         | 403    |
| `not_found`         | 404    |
| `conflict`          | 409    |
| `validation_failed` | 422    |
| `rate_limited`      | 429    |
| `internal`          | 500    |
| `unavailable`       | 503    |

`fields` is present only on `validation_failed`.

### 1.3 Pagination

**Keyset, not offset.** Offset pagination is wrong the moment a user adds a
purchase mid-scroll — rows shift and the next page silently skips one.

```
GET /v1/purchases?limit=20&cursor=<opaque>
→ { "items": [...], "nextCursor": "<opaque>" | null }
```

The cursor encodes `(created_at, id)` and is opaque to the client.

### 1.4 Idempotency

Every `POST` / `PATCH` / `DELETE` honors an `Idempotency-Key` header.

```
Idempotency-Key: <client-generated UUID>
→ Worker stores  idem:<user_id>:<key> → serialized response  in KV, TTL 24h
→ repeat request returns the stored response, no side effect
```

This is **required**, not optional. The offline outbox replays queued writes
exactly when the network is flaky, and without idempotency those replays create
duplicate purchases.

### 1.5 Rate limiting

Extend the existing KV fixed-window middleware from `/jobs/example` to all of
`/v1`: **120 req/min, keyed on user id** — not IP, which NATs many users
together. Keep the existing `x-ratelimit-remaining` / `x-ratelimit-reset`
response headers.

## 2. Endpoints

### 2.1 System

| Method | Path      | Notes                                                         |
| ------ | --------- | ------------------------------------------------------------- |
| `GET`  | `/health` | Unchanged shape; extend `checks` with Clerk JWKS reachability |

### 2.2 Identity

| Method   | Path                 | Notes                                                                                           |
| -------- | -------------------- | ----------------------------------------------------------------------------------------------- |
| `GET`    | `/v1/me`             | Profile + preferences. **JIT-provisions the `users` row on first call.**                        |
| `PATCH`  | `/v1/me`             | `reminderLeadDays`, `pushEnabled`, `timezone`. Changing lead days re-derives un-sent reminders. |
| `DELETE` | `/v1/me`             | Account deletion request → soft delete + enqueue `receipts.purge`                               |
| `POST`   | `/v1/webhooks/clerk` | Svix-verified `user.deleted` / `user.updated`                                                   |

### 2.3 Devices

| Method   | Path              | Notes                                                 |
| -------- | ----------------- | ----------------------------------------------------- |
| `POST`   | `/v1/devices`     | Register/refresh Expo push token; upsert on the token |
| `DELETE` | `/v1/devices/:id` | Unregister on sign-out                                |

### 2.4 Purchases

| Method   | Path                        | Notes                                                  |
| -------- | --------------------------- | ------------------------------------------------------ |
| `GET`    | `/v1/purchases`             | List **and search** — see query params below           |
| `POST`   | `/v1/purchases`             | Create; regenerates reminders                          |
| `GET`    | `/v1/purchases/:id`         | Detail; embeds `receipts[]`, `claims[]`, `reminders[]` |
| `PATCH`  | `/v1/purchases/:id`         | Partial update; regenerates reminders                  |
| `DELETE` | `/v1/purchases/:id`         | Soft delete — supports the PRD's undo affordance       |
| `POST`   | `/v1/purchases/:id/restore` | Undo within the window                                 |

**List/search query parameters**

| param              | type     | notes                                     |
| ------------------ | -------- | ----------------------------------------- |
| `q`                | string   | LIKE across `title` and `merchant`        |
| `category`         | enum     |                                           |
| `deliveryStatus`   | enum     |                                           |
| `from` / `to`      | ISO date | `purchase_date` range                     |
| `sort`             | enum     | `purchaseDate` \| `createdAt` \| `amount` |
| `cursor` / `limit` |          | keyset pagination, `limit` max 50         |

### 2.5 Receipts

| Method   | Path                         | Notes                                                       |
| -------- | ---------------------------- | ----------------------------------------------------------- |
| `POST`   | `/v1/purchases/:id/receipts` | **Multipart upload straight to the Worker**, streamed to R2 |
| `GET`    | `/v1/receipts/:id`           | `302` → short-lived signed R2 URL                           |
| `DELETE` | `/v1/receipts/:id`           | Deletes the row and the R2 object                           |

**On uploading through the Worker rather than presigning:** presigned R2 URLs
require S3-API credentials as additional secrets plus `aws4fetch`. Streaming a
phone photo (single-digit MB) through the R2 binding needs neither. Revisit only
if payload sizes grow.

Validate `content-type` against an image allowlist and enforce a size cap.

### 2.6 Claims

| Method  | Path             | Notes                                    |
| ------- | ---------------- | ---------------------------------------- |
| `GET`   | `/v1/claims`     | Filter by `type`, `status`, `purchaseId` |
| `POST`  | `/v1/claims`     | Open a return / refund / warranty claim  |
| `PATCH` | `/v1/claims/:id` | Status transitions, resolution fields    |

Status transitions are validated server-side — `completed` cannot go back to
`draft`.

### 2.7 Reminders

| Method | Path                        | Notes                                                                            |
| ------ | --------------------------- | -------------------------------------------------------------------------------- |
| `GET`  | `/v1/reminders`             | `?scope=upcoming\|history` — powers both the Reminders and Notifications screens |
| `POST` | `/v1/reminders/:id/dismiss` |                                                                                  |

`scope=history` returns `sent_at IS NOT NULL` ordered by `sent_at DESC`.

### 2.8 Metadata

| Method | Path                  | Notes                                                                   |
| ------ | --------------------- | ----------------------------------------------------------------------- |
| `GET`  | `/v1/meta/categories` | Category list plus **default warranty and return windows per category** |

Deadline dates are user-entered with category defaults prefilled. Serving those
defaults from the API rather than hardcoding them in the app means the windows
can be corrected without shipping an app release.

## 3. Async contracts

### 3.1 Queue messages (`ReminderQueue`)

```ts
{ type: "reminder.send", reminderId: string, userId: string }
{ type: "receipts.purge", userId: string }
```

Consumer config is unchanged from the existing demo consumer — batch 10,
`maxConcurrency` 4, `maxRetries` 5, `retryDelay` 60, DLQ on exhaustion. Only the
payload changes.

### 3.2 Cron — `0 2 * * *`

1. Keyset-scan
   `reminders WHERE fire_on <= today AND sent_at IS NULL AND dismissed_at IS NULL`
2. Join `devices`, filtered by `users.push_enabled`
3. Enqueue one `reminder.send` per reminder
4. Consumer batches ≤100 tokens per Expo Push request, then stamps `sent_at`
5. Check Expo push receipts; `DeviceNotRegistered` deletes the device row

**`sent_at` is written only after Expo accepts the message.** A crash mid-run
therefore re-sends at worst, rather than silently dropping a deadline warning.
For this product a duplicate notification is strictly better than a missed one.

Timezone: the cron scans a rolling window rather than an exact calendar day, so
users in any IANA zone get their reminder in local morning rather than at 02:00
UTC regardless of location.

## 4. Ownership and authorization

Every domain query is scoped by `user_id` from the verified JWT — never from a
request parameter.

A request for another user's resource returns **`404`, not `403`**. `403`
confirms the row exists, which leaks the existence of other users' purchases.
